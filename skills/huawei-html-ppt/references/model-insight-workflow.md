# 洞察分析：数据准备与研究流程

涉及人工基准、DFG 或多平台部署时，补充执行 [model-validation.md](model-validation.md)：核验 NoPE/RoPE、实际 forward 顺序、逐场景配方与最大 PP stage，并用已知错误回归检查拦截配置漂移。


用于 AI 模型研究、模型对比、机制拆解和实验分析，以及基于这些结果制作华为风格技术汇报。
流程为：问题与场景 → 证据采集 → 结构/算子清单 → 量化计算与核验 → 初步结论 → 绘图 → 排版。
开始分析时先按 [共用数据与分析](source-acquisition.md) 确认模型、特性和场景，按需读 [model-analysis-foundation.md](model-analysis-foundation.md) 建立可追溯、可复算的底稿。本文件侧重洞察分析如何组织判断与页面，不另建一套数据来源。
用户只要求分析时，交付数据与初步结果即可；需要汇报时按 [insight-analysis-style.md](insight-analysis-style.md) 进入洞察分析风格，复用共享绘图与导出流程。
本地组件库见 [model-diagram-components.md](model-diagram-components.md)，新增组件继续从实际语料和复用案例中验证。

## 适用范围与输入

- 典型任务：单模型洞察、模型代际变化、同类模型对比、关键模块解析、性能或成本分析、实验复盘。
- 用户只问一个模型知识点时，直接回答问题；不自动扩展成整套 PPT。
- 先利用已有材料确认：模型名称与版本、分析问题、受众、对比基线，以及论文、模型卡、代码、评测或参考图。
- 材料不完整时先整理已有证据；只有缺失信息会改变结论或分析方向时才追问。
- 最新模型信息、版本状态和评测数字需要核实；优先使用作者论文、官方模型卡、官方仓库及原始实验记录。

## 分析路径

围绕用户的问题选择必要维度，不要求每份汇报覆盖全部项目：

| 维度 | 要回答的问题 | 可用表达 |
|---|---|---|
| 定位与变化 | 解决什么问题，相对哪一版本改变了什么？ | 变化清单、前后对照 |
| 结构与机制 | 模块如何协作，数据或张量怎样流动？ | 架构图、局部放大图 |
| 能力与效果 | 在哪些任务上有效，证据是什么？ | 基准对比、消融表、误差或失败案例 |
| 效率与代价 | 延迟、吞吐、内存、计算或成本受到什么影响？ | 简单曲线、柱状图、条件明确的对比表 |
| 适用条件 | 什么场景值得采用，在哪些条件下不适用？ | 决策表、约束清单 |
| 验证与行动 | 尚缺什么证据，下一步怎样验证？ | 实验设计、待验证问题与行动项 |

工作顺序可按材料调整，先得到数据与初步结果，再进入绘图排版：

1. **界定问题与口径**：明确目标模型、版本、基线和比较条件。缺失参数写明未知，不补造配置。
2. **建立证据记录**：为重要结论记录来源文件/链接、页码/章节或代码位置；区分“来源事实”“分析推断”“待验证”。
   运行实现按需联合查看上游 vLLM 与 vLLM-Ascend，匹配版本并核对 patch/覆盖，按 [runtime-static-analysis.md](runtime-static-analysis.md) 追踪调度、缓存和执行调用链。
3. **取得初步结果**：按问题整理配置、层类型、Tensor/算子及 Shape 清单；计算必要的参数、权重、缓存、通信或实验指标。保留场景与统计口径，核验关键数值。
4. **形成初步判断**：连接“设计变化 → 可能影响的机制 → 已观测结果 → 适用边界”；没有消融或实验支持时不把相关性写成因果。判断引用具体结果，列出未知项。
5. **绘图与组织汇报**：从已核验的清单和结果生成图表，一页回答一个问题，结论附近给出关键证据。没有量化依据时使用定性结论或明确的问题式标题，不为凑标题编造数字。
6. **验证交付**：核对数字、图文一致性、来源和版面可读性，再按主 skill 的流程交付。只做研究时交付底稿与初步结论。

对比结果必须能解释测试条件：任务/数据集、模型版本、精度、硬件、输入输出长度、batch/并发等按相关性选取。
条件不同的结果明确分列或标注不可直接比较；总参数、激活参数、训练成本与推理成本分别说明。
实测、论文报告、估算值分别标记，估算注明假设与计算方法。

## 页面组织

页数和顺序服务于问题，不套固定长目录。可从以下页面中选择：

- **核心洞察**：少量关键判断、主要证据和适用边界；可复用摘要页，但按材料选择信息，不强塞无关参数。
- **模型结构**：整体架构与关键模块，标出数据流、控制流或张量维度；细节多时增加局部放大页。
- **机制拆解**：围绕一个技术点讲清输入、处理、输出、与基线的差异及代价。
- **证据与对比**：实验/消融、能力/效率对比和口径说明；参数表只列与分析问题相关的字段。
- **判断与下一步**：建议、限制、待验证假设与可执行实验。

制作汇报时阅读 [style-guide.md](style-guide.md)，复用页面品牌色、字体、页脚和页面组件，技术图内文字使用黑灰红，填充使用少量低饱和色。
默认交付单文件 HTML；用户明确要求可编辑 PPTX 时阅读 [pptx-conversion.md](pptx-conversion.md)。

## 绘图：保留结构与表达能力

先阅读 [drawio-diagram.md](drawio-diagram.md) 了解本地矢量与 XML 路径。
本分支按图的语义选择布局，复杂图的嵌入与布局按以下规则执行：

- 架构用分层/分组，执行过程用流程或时序，选择逻辑用分支，对比用同尺度并列；不把所有内容压成横向方框链。
- 显示必要的嵌套关系、分支、跳连、循环、共享模块、图例和输入输出；线型、箭头与颜色具有一致含义。
- 总览与局部细节可以拆页，不能为适应画布而删除决定机制的连接或把图缩到文字不可读。
- **保留 `.drawio` 为可编辑源文件**。有原始可编辑图时先检查并复用；重绘时核对节点、边、层级和标签。
- DFG 依据已核验的算子清单和数据流边生成，沿用节点 ID；图表关联结果 ID。数值变动先更新底稿并复算，避免图、表、正文各用一套数字。
- **优先尝试 draw.io 原生 SVG 导出**用于 HTML，验证渲染结果与源图一致，并确认无丢字、丢形状和外链资源。
  内置 server 的 `export_diagram` 提供 SVG/PNG 接口，但需实际启动浏览器并验证导出，不能仅凭接口存在宣布成功。
- 原生导出失败时记录具体原因；可用 PNG 保留外观并同时交付源图，明确该预览的编辑限制。
  手工重建 SVG 仅适合能核对等价性的简单图，不能默默把复杂图退化成基础方框。
- PPTX 中尽量使用原生文本与形状；未能转成原生对象的图需单独说明，并附 `.drawio`，不能宣称整张图已原生可编辑。

逐图检查：语义完整、连线连接正确、无交叉遮字、缩放后可读、源图与预览一致。
本地路径已用 Kimi K3.1 案例验证：张量堆叠、矩阵、柱体状态、专家分支、设备分组和原生表格分别生成 HTML 与可编辑 PPTX，仍需逐图验证语义和版面。

## 从新语料沉淀组件

用户提供新图、PPT、PDF 或技术材料后，先识别原图表达的问题，再提取组件：

1. 定位页码/图号与来源，区分可编辑形状、矢量图和截图；截图重建结果标注为重建。
2. 拆出基本模块与组合结构，同时保留有意义的层级、接口、连接点、标签和图例。
3. 为每个候选组件记录：名称与用途、输入输出/连接点、可调整部分、组合约束、来源、适用边界、验证状态。
4. 用一个新的分析场景验证组件可复用，再纳入库；不把某个模型的专有结构误当通用模块。
5. 首批组件确认后再建立 `assets/diagram-components/`：每个组件保留 `.drawio` 源文件和可查看预览，
   用 `references/model-diagram-components.md` 索引实际存在的组件及适用范围。

试用反馈要区分原因：语义拆解、组件缺失、布局表达或渲染导出。
优先修正对应层，并用反馈中的同一实例复核；成熟规则再写回本流程或组件索引。

## 支持边做边学

用户希望学习时，可按“概念 → 机制 → 图示 → 证据 → 局限”解释关键技术，并结合当前材料给出一个可验证问题。
把来源结论与自己的推断讲清楚，允许逐层展开；学习说明按需单独提供，不强塞进正式汇报。

## 洞察结论与昇腾亲和

执行 [insight-analysis-style.md](insight-analysis-style.md)。每页包含本页分析结论；A3/A5 等目标硬件需要分别呈现量化/内核、混合缓存、通信、P/D 并行与部署形态。用户已确认的基准默认沿用，建议与待验证事实明确分开。材料以信息集中为目标，优先合并重复参数、背景和路线图。
