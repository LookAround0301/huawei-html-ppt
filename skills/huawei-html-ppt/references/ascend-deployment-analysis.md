# 昇腾部署分析：从结构变化到具体方案

用于需要A3/A5或其他昇腾代际部署建议的模型洞察。先理解本次模型的执行与存储，再给出各平台的部署起点。硬件代际名称不自动决定容量、设备寻址、精度或支持状态。

## 固定场景，再比较

- 确认物理卡、die、可见设备/rank与节点的映射。分别给P、D的节点数和总rank；需要卡数时按真实硬件映射换算。TP/EP/PP与DCP的进程组关系要核对，不能把所有参数直接相乘。
- 固定模型版本、请求长度、并发、原生与部署权重格式、每类Cache的dtype与分片、PP层分配和已计运行时开销。用户提供可信基准时沿用，另设候选方案应并列说明变动。
- 原生低比特专家不等于Attention、共享专家或所有Linear都可同精度运行。分项列出dtype和切分；来源不支持的部署配方保留为假设。
- 代际或模型对比先保证口径一致。更换节点数、缓存精度、共享专家复制方式或运行时预留后，不能把显存差额直接归因为模型变化。

## 从结构解释资源与通信

| 已确认的结构或测量 | 要继续分析的问题 |
|---|---|
| 新增索引、压缩或检索路径 | 主注意力访问减少后，索引计算、离散访存和格式转换是否成为主要成本？ |
| 全历史Cache与固定状态并存 | 哪些随上下文/并发增长，哪些固定；每种状态是否受TP、CP、DCP或PP分片？ |
| 专家多、每token激活少 | 权重驻留按部署的专家全集核算；派发、共享专家与热点负载分别如何影响策略？ |
| Prefill与Decode负载不同 | 是否需要分开选择PP、TP、EP和上下文并行；P/D交接需要哪些真实持久状态？ |

这些是分析问题，不是跨模型通用结论。只有实现或profile支持时，才称某项为瓶颈。状态传输按实际缓存接口列出，不把层内临时张量当持久状态搬运。

## 每个平台的正文应能回答

1. **怎么部署**：给出具体P/D组合、各自规模、量化和请求条件。推荐容量起点、性能候选与已测方案分别说明。
2. **为何容纳得下**：用相同rank口径列权重、各类Cache/状态、已计buffer和运行时预留。P取同一stage各项之和的最大值，D按对应实例/rank；不要相加不同stage的分项最大值。
3. **哪里限制扩展**：结合分项解释更长上下文、更大并发或扩大EP/DCP的收益与代价。某类Cache不受DCP分片时，不能把总Cache按DCP倍数缩小。
4. **为什么选这个起点**：把结构、容量与通信联系起来。账面余量不能直接换算成并发上限；“最小、最优、必须扩容”需要相应比较或实验依据。

源表只有权重+Cache小计、另一份可信基准补充系统开销时，两者分列并标清范围。没有依据不要固定采用某个OS预留、HCCL大小或容量百分比。HCCL配置上限不等于实测驻留。

## 页面与组件

涉及两个平台且信息充分时，优先各用一页：权重分项、缓存随上下文变化、总预算和部署示意。必要时另页说明并行通信与状态交接，页数由信息量决定。结论写成具体配置、结果和选择理由，方法见 [结论写法](insight-conclusions.md)。

- `comparison-table`承载同口径变化；`memory-budget`承载已核算分项，不暗示剩余都可用。
- `pd-state-transfer`承载P/D规模与实际状态交接。传入P/D各自的`nodes`、`cards_per_node`、`ranks_per_node`、`parallel`及`states`，不内置硬件或模型配置。
- 交接图还不能说明通信域时，补充节点内TP/DCP与跨节点EP路径。只画两个计算池和一根箭头不能替代通信分析。

最后核对：图表和结论使用同一场景；卡/rank口径一致；主KV与索引/递归状态没有合并套用切分；系统开销只计一次；实际可复用路径和待适配路径分清。细项检查见 [基准与场景校验](model-validation.md)。
