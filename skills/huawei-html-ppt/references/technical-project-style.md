# 技术项目风格

用于 PDCP/TDR、立项、技术规划、阶段评审与项目进展。优先按“读者需要判断什么”组织材料。

涉及模型或推理特性的项目，先按 [共用数据与分析](source-acquisition.md) 建立“模型结构 → 特性作用 → 当前实现 → 场景结果”的底稿，再组织目标、方案、进展和验证。没有项目计划或实测记录时，不从源码存在推断已交付或目标已达成。非模型项目直接使用项目材料。

## 选择页面，而不是固定一套标题

| 用途 | 页首与结构 | 默认布局 |
|---|---|---|
| 多项目定位 | 项目定位 → 各项目挑战 → 对应专题 | `project-landscape` |
| 一个项目的多个专题 | 项目名称 → 专题目标 → 项目节点 → 技术布局 / 技术点进展 | `project-portfolio` |
| 单专题立项/方案 | 挑战＋目标 → 方案与验收 | `project-solution` |
| 单专题进展/评审 | 目标＋进展 → 方案/结果 | `project-progress` |
| 技术到版本的协同 | 协同目标 → 技术线 / 版本线 → 交接与准入 | `project-coordination` |
| 解释细节 | 一句作用 → 技术点 / 做什么 / 解决什么问题 | `project-explainer`（附录） |

“挑战＋目标 / 目标＋进展”继续用于单专题；项目组合页采用用户正式版的“专题目标＋节点＋布局 / 进展”。不要再给组合页强加成对摘要，或把每个技术点都拆成正文一页。

## 正文：项目组合页

- 每页通常容纳一个项目的1–2个相关专题，标题用项目名称，分册时可用1/2、2/2。数量服从可读性，不固定页数。
- 顶部用浅灰带列专题目标，红色只突出专题名和关键判断。数值带场景与比较基线。
- 下方放紧凑的评审节点带，当前节点用红，其余灰。日期是计划、实际还是待定必须区分；不能把计划日期写成已完成。
- 主体左侧约42%为技术布局，右侧约56%为技术点进展，两侧专题顺序和行高对应。主题多寡不同可调比例，不机械五五开。
- 每个专题右侧先有一句“总进展”，说明达成程度、主要成果与缺口，再以2–3列短段落列技术点。它承担项目页的分析结论，不额外加洞察分析的通栏结论框。
- 技术点名称与布局节点保持一致。正文写“动作 / 产物＋状态或结果＋必要条件”，不要堆满原始周报。
- 原型、仿真、单算子、整网和客户结果分清；一期基础和本期成果分清。实测场景不同于目标场景时，应在结果旁说明。

项目名称、专题名称和具体事项可以直接作标题；正文用准确术语写清做了什么、当前结果和未完成项，避免抽象套话。写法见 [style-guide.md](style-guide.md)。

## 信息分层

主线保留定位、目标、布局、总体进展和关键证据。机制解释和术语放到按专题组织的附录，用“技术点 / 做什么 / 解决什么问题”说明。不要只因附录增加就认为主线不集中。

技术协同计划区分技术验证与版本承接，两条时间轴之间说明交接条件、主导责任和依赖。需要商发时显示对应准入条件，不把所有日期排成互不相关的事项清单。

项目名称标题、主题目标与总进展已能表达判断时，不再强制长句结论标题。封面和目录只导航；是否加入随材料长度与用户模板决定，不固定复制正式版27页。

## 原图优先

技术项目涉及 vLLM-Ascend 等已有实现时，先找现成技术图：用户指定材料优先，其次检查对应版本仓库的 `docs`、图片目录及文档链接，再查模型发布方或官方论文。记录所用仓库 commit、文件路径，或论文版本、图号/页码；核对图描述的模型、特性和实现与本次分析相符。不能只因图片出现在仓库中就认为适用于当前实现。

区分当前文档直接引用的图、仓库遗留资产和论文算法图。旧图仍可帮助解释原理，但图中的拓扑、参数或支持范围必须单独核对；与当前实现冲突时，换用匹配的原图或用表格解释，不把旧参数当部署建议。源码存在、测试文件存在、本轮实际运行通过也要分清。

- 原图能准确解释内容时直接本地复用，不为统一配色、使用组件或追求可编辑而重画。保留原图颜色和标签；新增标题、说明与批注仍用黑灰红。
- 等比例完整展示，不拉伸、不裁掉图例、关键分支和条件；图片过密时先放大或拆页。需要局部放大时保留原图对应关系，并在备注记录裁切范围。
- 只有没有合适原图、原图与当前实现不符，或放大/拆页后仍无法阅读时，才按已确认绘图标准补画或改绘。备注写明原因、继承部分和改动，不能把自绘图说成官方原图。
- 来源和制作说明放隐藏元数据/PPT备注，不额外占据正文。嵌入本地图片，交付 HTML 不依赖外部图片链接；原材料仍留在本地，不加入公开 skill 仓库。

运行接口支持普通页 `type:"image"` 和组合页 `topic.image`，具体字段见 [runtime-contract.md](runtime-contract.md)。原图不输出虚假的可编辑 SVG/draw.io；需要编辑的新增覆盖标注单独保存。

## 原图和分析怎么搭配

按图的形状和信息密度选择，不固定整篇页数或一律左右均分。可复用的局部版式在 `assets/units/source-figure-layouts.json`：

| 内容 | 布局 | 编排重点 |
|---|---|---|
| 原理概览＋项目进展 | `project-figure-overview` | 左侧原图与短对照表，右侧集中写实现、当前进展和下一步 |
| 原图＋数据/实现核验 | `project-figure-evidence` | 左图右表，表格写清对象、当前实现与判断，避免原文重复 |
| 复杂通信/存储原图 | `project-figure-full` | 原图通栏，目标与进展放顶部摘要，不再挤入旁栏 |

近方形的图需要高度，宽图需要横向面积；内容少时调列宽、图的面积和相关页组合，不能拉伸原图或靠小字挤满。有合适原图的机制页优先用图；状态依赖、实现边界、配置条件和验收项没有合适图时，用简洁表格承载，不硬造流程图。表格结论应解释实际影响或下一步，不只复述参数。

HTML 原图可点击或按 Enter 放大，再切换原始尺寸；Esc 关闭，放大期间不切换幻灯片。放大用于查看细节，不能代替正文正常尺寸的可读性验收。核心包只保留布局、样式与交互组件，原图与完整报告留在本地。

## 视觉与实现

技术布局可以用结构图，性能、资源和进展证据优先用简单曲线、柱状图或对比表；复杂分析图按需要简化或放附录，按 [chart-selection.md](chart-selection.md) 选择，不强制每页放流程图。

使用细灰围栏、短红角线、骑线模块标题、灰表头和选择性红字。详见 [project-report-reference.md](project-report-reference.md)。正式组合页优先用 `scripts/render_project_report.py` 和 `assets/project-report/`，旧单专题页继续用共享渲染器。

**新绘图标准不变**：沿用 [reference-diagram-fidelity.md](reference-diagram-fidelity.md) 的结构保真、黑灰红文字、低饱和填充。项目布局变化不能把已确认的图降级成通用方框链；复用原图按上面的原图优先规则保留原貌。

有 xlsx 时从结构化来源直接注入数据。来源与制作批注只放隐藏元数据 / PPT备注；场景条件、未完成项和术语解释属于内容，可以正常显示。明确要PPTX时按转换流程保留原生对象。

版面尽量减少大块无意义留白；图表占比、栏宽、行高和页数按内容调整，具体执行 [style-guide.md](style-guide.md) 的“尽量减少留白”规则。
