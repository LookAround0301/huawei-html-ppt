# 两种风格共用的数据与分析

用于模型洞察，以及涉及模型、推理特性的技术项目。先形成同一份可追溯底稿，再按汇报用途选择表达；风格不决定数据来源。普通项目没有模型关联时，直接整理项目材料，不强制执行模型分析。

先用用户提供的报告/源码/配置/基准。用户已确认准确时沿用，除非本次明确要求审计；缺失部分才按下面的来源补充。不是每个任务都要运行所有工具。

## 共用来源

| 来源 | 主要用途 | 不能替代 |
|---|---|---|
| https://github.com/maoxx241/se-tools | 分析工具、计算方法、参数与部署推演入口 | 官方模型配置、硬件实测 |
| https://gitcode.com/gcw_hasgjVbP/model_analysis | 模型分析流程、配置与计算产物的组织 | 被分析版本的实际 forward |

| https://github.com/vllm-project/vllm-ascend | Attention 后端、Cache、通信与并行实现、兼容约束 | 上游模型算法说明或实际收益 |
| https://github.com/vllm-project/vllm | 按实际调用链检查上游调度、批处理、KV/Prefix Cache 管理、模型执行及并行分组 | Ascend patch 后的实际行为、NPU 算子支持或硬件实测 |

记录仓库 revision、路径、符号/章节、访问日期和证据等级，来源元数据放备注。模型身份不明时不猜 HF 仓库名；先找发布方链接或让用户补充身份信息。

## 先理解模型，再分析相关特性

围绕当前问题建立“模型/版本＋特性＋运行场景”，只收集会影响判断的信息，不因选择技术项目风格就跳过模型结构，也不因选择洞察风格就忽略实现进展。

1. **模型结构**：确认层型、Attention/MoE、关键 Tensor、缓存及递归状态；涉及版本对比时保留基线与变化位置。
2. **运行实现**：把这些模块映射到匹配版本的 vLLM / vLLM-Ascend 调用链，核对实际后端、patch、条件开关和已有测试。
3. **特性作用**：说明作用在哪些模块，怎样改变计算、存储、通信或调度，哪些模块不适用，以及组合使用的约束。不能由一个后端支持推断整模型支持。
4. **场景结果**：按相关性核对硬件、rank、精度、P/D、并行、上下文和并发；计算必要指标，分清已有材料、静态估算、代码证据与实际测量。
5. **判断与缺口**：用结果说明收益、代价、适用范围和下一步验证。同一特性换模型、版本或场景后，重新核对受影响部分，不直接继承支持结论。

例如 PCP/DCP：先区分模型的 Attention 历史 KV、Indexer、recurrent/conv state，再检查它们各自的分片、复制、通信和交接规则。模型结构解释“为什么有这些约束”，实现代码说明“当前做到哪里”，测量结果才说明“实际收益多少”。

详细计算复用 [模型分析底稿](model-analysis-foundation.md)，调用链复用 [运行实现分析](runtime-static-analysis.md)。不需要完整参数核算的任务，只分析与该特性有关的层、状态和路径。

## 一份底稿，两种表达

| 共用内容 | 洞察分析侧重 | 技术项目侧重 |
|---|---|---|
| 结构、特性机制和实现路径 | 变化原因、局部影响和适用条件 | 技术问题、方案及关键实现 |
| 同口径结果和证据 | 收益、代价、部署建议 | 当前完成程度、达成结果 |
| 支持条件与未知项 | 结论边界与进一步验证 | 未完成项、依赖和下一步 |

沿用 [模型分析底稿](model-analysis-foundation.md) 中 `sources.json`、`model-facts.json`、`scenarios.json`、`results.json`、`findings.md` 等文件的组织建议；运行路径可存于 `runtime-analysis.json`。按需在 findings 中关联“特性 → 模块/状态 → 实现 → 场景 → 结果/限制”，不为凑格式生成空文件。

两种汇报引用相同的来源、结果 ID、单位和状态口径；不为适应页面单独改数据。技术项目中的目标、计划和项目进展还需来自用户材料或真实验证记录，不能从静态源码推算完成百分比。

## 取图与证据边界

技术项目先检索用户材料、对应版本仓库的 `docs` 页面及其引用图片、模型发布方材料和官方论文。已有原图与当前模型/特性/实现匹配就直接本地复用，记录 commit/路径或论文版本/图号，不默认重绘；具体见 [原图优先](technical-project-style.md#原图优先)。缺少匹配图时再补画。

画图或选用原图前将 config 和 forward 的顺序交叉核对，再检查运行后端如何实现。不把源码某分支存在等同于任意型号、任意版本可用。以 Kimi K3.1 为例，先保留已验证 K3 主干，再定位 K3.1 新增/修改的子图，并把增量放大；不能拿其他模型的数值或层数填空。

涉及调度与缓存生命周期时，先检查 vLLM-Ascend 的版本依赖、插件注册、patch 和覆盖，再沿调用链阅读对应版本的上游 vLLM。没有覆盖且调用解析到上游时，才按上游实现说明行为。不要把两个仓库各自的最新 main 直接拼在一起推导支持性；详细步骤见 [runtime-static-analysis.md](runtime-static-analysis.md)。

下载公开文件可用网络；本地保密材料不发送到搜索、云文档、外部绘图、翻译或生成服务。页面说明不要夹带本机私有路径或未授权发布的数据。
