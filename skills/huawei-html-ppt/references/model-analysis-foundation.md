# 模型分析底稿：先取得数据与初步结果，再绘图排版

涉及人工基准、DFG 或多平台部署时，补充执行 [model-validation.md](model-validation.md)：核验 NoPE/RoPE、实际 forward 顺序、逐场景配方与最大 PP stage，并用已知错误回归检查拦截配置漂移。


本规范将分析与呈现分开：先形成可追溯、可复算的底稿，再从底稿制作技术图和汇报页。
它是模型洞察与模型相关技术项目的共用计算基础，入口见 [共用数据与分析](source-acquisition.md)。特性依赖模型结构时，按“模块/状态 → 实现路径 → 场景结果”选取必要的分析内容，不要求每个项目都核算整模型。
用户只要求分析时，交付数据、计算结果与初步判断即可，不自动制作 PPT。

## 研读来源与适用边界

以下版本用于记录方法参考。实际分析需匹配本次任务的模型与运行环境，不将仓库样例当成当前模型或设备的实测结论。

| 来源与固定版本 | 重点吸收 | 使用边界 |
|---|---|---|
| [se-tools](https://github.com/maoxx241/se-tools/tree/c3569480ac779dbb8852fcce91e53b77670025a5)，`c3569480ac779dbb8852fcce91e53b77670025a5` | 配置/代码到 Tensor 清单；可复算的权重、缓存与通信；显存场景；来源哈希与独立校验 | 引擎按模型适配，不能只换名称/维度；其离线算术验证不证明设备上的性能 |

两套工具需按当前模型适配并验证。下载仓库不等于运行了全部流程，离线计算也不代表已完成 NPU 性能测试。

## 1. 先定义分析对象与场景

最少确定模型/版本、研究问题和比较基线。涉及部署时再增加相关场景参数：

- 模型范围：语言主干、视觉塔/投影器、MTP/draft、共享权重是否计入。
- 阶段和负载：Prefill 或 Decode；batch/并发、当前步 token、历史长度、输出长度、前缀命中率。
- 并行与精度：TP/DP/EP/PP/CP 的实际分组和层归属；权重、激活、KV、Indexer、通信各自的 dtype。
- 运行环境：模型、vLLM、vLLM-Ascend 与算子库版本，Ascend patch/覆盖，硬件与可用内存，实际支持的量化和通信路径。

仅在影响当前问题时补充字段。未知字段保留未知，不套用历史案例的 EP、带宽、量化或上下文默认值。

## 2. 收集小体积证据，建立来源清单

优先读取已有材料；需要补充时收集配置、模型卡、建模代码、权重索引、实验/Profiling 记录。
模型仓库默认只获取这些小文件，不为结构分析下载完整权重。

每份证据记录来源 URL/本地文件、revision、文件 SHA-256、采集时间及实际检查的位置。
固定同一次分析使用的版本；配置、代码、权重或部署文档来自不同版本时明确列出差异。

不同材料能证明的内容不同：

- 模型卡说明作者声明、目标场景与部署建议；不能代替实测。
- 配置声明维度与开关；代码确认实际 forward、分支、权重共享与缓存更新。
- `weight_map` 证明权重名称和分片归属，**不直接提供 Tensor shape/dtype，也不证明某条 forward 路径被执行**。
- 需要检查真实权重存储时，读取已有 Tensor 元数据或按需获取 Safetensors 头；与完整权重下载区分。
- 历史 HTML/PPT 用来找分析问题与参考表达，数字和架构判断回到对应版本的底层证据核对。

## 3. 建立结构、算子和 Tensor 清单

先确定层类型与重复次数，再展开每种不同层的 forward。共享模块、跨层缓存、MTP、视觉分支单独登记。

| 清单 | 必要内容 |
|---|---|
| 模型事实 | 配置原字段、统一含义、值、单位、来源；层类型/层号与包含范围 |
| Tensor | 唯一 ID、模块、名称、shape、dtype、重复数、共享关系、量化附加数据、分片/复制规则、来源 |
| 算子 | 唯一 ID、层类型、阶段、算子或融合组、输入/输出 Tensor ID、Shape、dtype、功能、代码位置 |
| 数据流边 | 源节点/端口、目标节点/端口、Tensor ID；残差、路由、缓存读写与控制边分别标注 |

Shape 中 B、S、T 等运行时维度保留符号并定义含义；从配置确定的维度填写具体值。
算子前后维度需要能对上。权重存在与算子实际执行分别记录，不能只凭名称推断融合、加载或调度行为。

## 4. 计算需要回答问题的指标

### 权重、参数与单卡占用

以 Tensor shape 的乘积和真实重复/共享关系计数；总参数、激活参数和存储字节分别输出。
激活参数注明 Embedding、LM head、共享专家、路由器、MTP 等统计口径。

存储字节包括主权重以及 scale、zero-point、packing/padding 等已知附加项。
FP4 的 `0.5 B/元素` 只描述理想主载荷；不能据此把整个 checkpoint、缓存或通信都按 0.5 B 计算。
分片后按局部 shape 计算量化分组和元数据；DP 复制、TP/EP 分片和 PP 层归属分别处理。
专家不能整除时检查实际放置规则，最大单卡占用不能仅用全局总量除以 EP。

报告至少区分：checkpoint 存储、驻留权重、缓存/状态、临时 buffer、其他运行时开销。
只计算了权重时，结论写“权重占用”，不写“完整部署显存”或直接保证可部署。
跨 PP stage 比较时取每个 stage 完整总量的最大值，不把不同 stage 的独立最大项相加。

### 缓存与状态

分别计算每层/每 token、每请求、当前场景及每 rank 的缓存，并标注逻辑保留量或物理分配量。
核对 K/V 维度、MLA absorption、Indexer、窗口/池化/尾部缓存、跨层共享、量化元数据与 block 对齐。
线性注意力的 recurrent/conv state 独立计入，不按普通 KV 乘历史 token 数。
压缩前后比较使用相同场景、dtype 和统计范围，不把“压缩倍率”直接等同于加速倍率。

### 通信与性能

通信事件记录阶段、调用位置、通信域、API count 语义、Tensor/dtype、调用次数和算法假设。
区分单 rank、单通信组、整部署；区分本地拷贝、端点载荷和物理链路字节。
AlltoAllV 有实测计数矩阵时按矩阵算；均匀路由比例只是显式假设，不能重复乘跨 rank 比例。
P→D 交接量与逐步 collective 分列；同一调用的模块视图不能重复求和。

没有运行时证据时，只输出有假设的通信量或敏感性估算。
例如带宽变为原来的 `1-d`，被影响的纯带宽耗时项变为 `1/(1-d)`；整体 forward 还依赖通信占比、覆盖与重叠。
理论载荷不能直接推导真实吞吐、MFU/MBU、链路拥塞或端到端延迟。

## 5. 形成初步结果并核验

每个结果保留 `result_id`、值与单位、场景 ID、统计范围、输入/计算版本、证据引用、公式/方法及限制。
明确区分：来源报告值、静态计算值、场景估算值、设备实测值；未知结果不补成 0。

最低核验：

- 关键字段与配置/代码一致；Tensor 共享、层数和重复数没有重复计入。
- 用独立推导检查关键总量，并与可用的权重元数据/官方口径对账；差异给出解释或保留未解问题。
- 单位统一：GB/GiB、GB/s/Gb/s 分开；“1M token”先写清是 1,000,000 还是 1,048,576。
- 检查代表性边界：并行度 1、专家不整除、PP 不均匀、量化 scale、缓存对齐、共享/复制关系。
- 测试通过只证明覆盖到的计算行为，不替代框架、硬件与模型支持性验证。

初步结论采用“判断 → 支撑 result_id → 适用条件 → 未知项 → 下一步验证”。
适配优先级依据指定版本的实际缺口和影响判断：已有支持、部分支持、缺失、待确认；不因出现 MoE/MLA 就自动列为 P0。

涉及运行行为的结论同时记录实现归属：上游继承、Ascend 覆盖/扩展、条件分支或待确认。存在上游实现不等于 NPU 路径可用，存在 patch 也不等于当前配置启用了它。

## 6. 留存可复用底稿，再进入绘图

小任务至少保留来源、结构化结果和初步结论。复杂任务按需分成以下文件，不生成无内容的占位文件：

| 文件建议 | 用途 |
|---|---|
| `sources.json` | 证据版本、文件哈希与来源位置 |
| `model-facts.json`、`tensors.csv` | 配置事实、结构、权重与共享/分片清单 |
| `operators.json` | 节点、边、Shape 与代码证据；供 DFG 使用 |
| `scenarios.json` | P/D、负载、并行、精度和硬件等场景输入 |
| `results.json` 或 `results.csv` | 可供图表读取的量化结果和统计口径 |
| `findings.md` | 初步结论、依据、边界和待验证问题 |
| `validation.json` | 运行命令、检查结果与未覆盖范围 |

从底稿选图：结构/算子清单生成架构与 DFG；逐组件数据生成内存分解；场景扫描生成趋势/权衡；版本差异生成对比图。
DFG 节点和边沿用算子清单 ID，图表数据关联 `result_id`。汇报数字需要修改时先改输入并复算，不单独改图片或幻灯片上的数字。
数据与初步结论达到当前问题所需的证据程度后，再按用途进入 [洞察分析](model-insight-workflow.md) 或 [技术项目](technical-project-style.md) 的组织与排版流程。

## 工具复用时检查

- 路径、模型维度、量化范围和专家放置若被硬编码，应改成显式输入并重新验证。
- 仓库概述、配置与实际forward不一致时，保留差异并核对版本；不直接沿用摘要。
- 纯EP公式、固定适配优先级和通用性能结论都有前提，按目标模型与运行环境确认。
- 两套工具可交叉核验关键结果，报告样式仍由本skill控制。
