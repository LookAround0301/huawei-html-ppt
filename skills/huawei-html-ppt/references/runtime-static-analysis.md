# vLLM 与 vLLM-Ascend 联合静态分析

用于解释调度、KV/Prefix Cache、P/D、模型执行与并行分组的运行行为。按当前问题追踪必要路径，不要求每个任务遍历整个仓库。

- 上游：[vllm-project/vllm](https://github.com/vllm-project/vllm)
- Ascend 插件：[vllm-project/vllm-ascend](https://github.com/vllm-project/vllm-ascend)

## 先固定可对应的版本

记录模型 revision、vLLM revision/tag、vLLM-Ascend revision/tag，以及存在的本地补丁。优先从用户环境和依赖声明确认组合；没有现成环境时选有版本兼容依据的组合并注明分析范围。不能把两仓库任意最新 main 的代码拼成一套运行结论。

本地仓库、原始文件和分析产物保存在任务目录；不把整仓库纳入 PPT skill。只有必要文件时按需下载。用户保密材料不上传。

## 沿实际调用链找实现归属

1. 从配置、模型注册和插件入口确认使用的引擎/后端路径。文件和类名随版本变化，按当前版本检索，不固定套旧路径。
2. 在 Ascend 侧检查插件注册、继承重写、patch/monkey patch、替换函数与条件开关，确认是否修改了目标行为。
3. 从入口向下追踪调用。未被覆盖且确实调用上游时，再到对应 vLLM 版本读取实现；有覆盖时以实际替换路径为准，并记录与上游的差异。
4. 调度、缓存管理与设备执行分别定位，再连接为调用链。NPU 内核、数据格式和通信实现回到 Ascend 路径验证。

## 按问题选检查点

| 问题 | 重点检查 |
|---|---|
| 调度与批处理 | 请求状态、token预算、chunked prefill、抢占/恢复、Prefill与Decode如何进入执行批次 |
| KV/Prefix Cache | block分配与释放、缓存组、命中条件、生命周期，以及混合注意力/循环状态的处理 |
| P/D分离 | scheduler、connector与runner的交接，传输哪些状态，接收端如何恢复或重排 |
| 模型执行 | 具体模型类、runner、attention backend、图模式与动态路径、量化加载和算子调用 |
| 并行通信 | TP/DP/EP/PP/CP/DCP的进程组构造、参与rank、collective触发点与张量大小 |

不要从配置字段名称直接推出行为。检查该配置是否进入当前路径、参与什么分组，以及张量如何流动。

## 记录证据与限制

重要结论记录：特性、配置条件、两个仓库的版本、调用链、patch/覆盖位置、文件/符号/行号和判断依据。实现归属分为：

- **上游继承**：当前配置的调用链落到已核对的上游实现。
- **Ascend 覆盖/扩展**：插件或补丁改变了对应行为。
- **条件路径**：仅在特定开关、精度、硬件或后端下成立。
- **待确认**：版本关系、动态替换或实际调用无法确定。

在需要时把这些字段写入任务的 `runtime-analysis.json`，与模型事实和计算结果关联。绘图时区分调度决策、缓存管理、设备计算与通信，保留真正的数据/控制关系。

静态分析能说明代码路径与约束，不能代替实际运行验证、性能测量或完整NPU支持结论。来源和详细调用链放备注/底稿，影响判断的启用条件和未验证项放在正文。
