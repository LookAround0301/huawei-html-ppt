# vLLM 与 vLLM-Ascend 联合静态分析

用于解释调度、KV/Prefix Cache、P/D、模型执行与并行分组的运行行为。按当前问题追踪必要路径，不要求每个任务遍历整个仓库。

- 上游：[vllm-project/vllm](https://github.com/vllm-project/vllm)
- Ascend 插件：[vllm-project/vllm-ascend](https://github.com/vllm-project/vllm-ascend)

## 先固定可对应的版本

记录模型 revision、vLLM revision/tag、vLLM-Ascend revision/tag，以及存在的本地补丁。优先从用户环境和依赖声明确认组合；没有现成环境时选有版本兼容依据的组合并注明分析范围。不能把两仓库任意最新 main 的代码拼成一套运行结论。

本地仓库、原始文件和分析产物保存在任务目录；不把整仓库纳入 PPT skill。只有必要文件时按需下载。用户保密材料不上传。

## 沿实际调用链找实现归属

1. 从配置、模型注册和插件入口确认使用的引擎/后端路径。文件和类名随版本变化，按当前版本检索，不固定套旧路径。
2. 在 Ascend 侧检查插件注册、继承重写、patch/monkey patch、替换函数与条件开关，确认是否修改了目标行为。
3. 从入口向下追踪调用。未被覆盖且确实调用上游时，再到对应 vLLM 版本读取实现；有覆盖时以实际替换路径为准，并记录与上游的差异。
4. 调度、缓存管理与设备执行分别定位，再连接为调用链。NPU 内核、数据格式和通信实现回到 Ascend 路径验证。

## 按问题选检查点

| 问题 | 重点检查 |
|---|---|
| 调度与批处理 | 请求状态、token预算、chunked prefill、抢占/恢复、Prefill与Decode如何进入执行批次 |
| KV/Prefix Cache | block分配与释放、缓存组、命中条件、生命周期，以及混合注意力/循环状态的处理 |
| P/D分离 | scheduler、connector与runner的交接，传输哪些状态，接收端如何恢复或重排 |
| 模型执行 | 具体模型类、runner、attention backend、图模式与动态路径、量化加载和算子调用 |
| 并行通信 | TP/DP/EP/PP/CP/DCP的进程组构造、参与rank、collective触发点与张量大小 |

不要从配置字段名称直接推出行为。检查该配置是否进入当前路径、参与什么分组，以及张量如何流动。

## 记录证据与限制

重要结论记录：特性、配置条件、两个仓库的版本、调用链、patch/覆盖位置、文件/符号/行号和判断依据。实现归属分为：

- **上游继承**：当前配置的调用链落到已核对的上游实现。
- **Ascend 覆盖/扩展**：插件或补丁改变了对应行为。
- **条件路径**：仅在特定开关、精度、硬件或后端下成立。
- **待确认**：版本关系、动态替换或实际调用无法确定。

在需要时把这些字段写入任务的 `runtime-analysis.json`，与模型事实和计算结果关联。绘图时区分调度决策、缓存管理、设备计算与通信，保留真正的数据/控制关系。

静态分析能说明代码路径与约束，不能代替实际运行验证、性能测量或完整NPU支持结论。来源和详细调用链放备注/底稿，影响判断的启用条件和未验证项放在正文。

## 把实现画进模型结构

模型结构图先走读匹配版本的 vLLM-Ascend 模型入口、实际 backend 与算子调用；继承部分沿调用链查对应 vLLM。没有对应 Ascend 实现时，再用 Hugging Face 源码或用户提供的结构/实现材料绘制。HF/config 同时用于交叉核对模型语义与维度。有 Ascend 实现时，用实际执行路径表达运行图；未找到接线证据时保留原理图并说明范围，不借用其他模型的融合算子充当已适配实现。

- 把关键融合体画成节点，可用缩写，正文或图例解释缩写。区分合并投影、真正的计算融合、计算通信融合和只在 Python 中组合的小算子，不因类名含 Fused 就视为单内核。
- 核对融合的硬件、版本、量化、布局和开关条件；条件分支及 fallback 要能追溯。Prefill 与 Decode 不同就分别画，不能套同一条链。
- 在投影、reshape、head 分片、专家分发与合并、缓存写入和通信前后按需标 shape。先定义符号和统计口径，区分逻辑张量、每 rank 张量、分页/填充后的物理布局。通信后的 token 数、head 数可能变化，不能一律除以 TP。
- 完整维度来自本次 config，局部维度来自实际分片代码。只标有依据且帮助理解的变化，未知用符号或明确待确认；量化打包字节数与 scale 另算，不将其当逻辑 hidden 维度。
- `T` 可表示当前算子批次的 token 数，不能默认为整条上下文；`S` 是历史长度。MoE 分发后的 `M` 由路由/接收负载决定，不能默认各 rank 都是 `T×TopK/EP`。
- 验收要将关键节点、条件、shape 与源文件/符号/行号逐项核对，并检查图内没有误添 RoPE、误删门控、漏掉状态读写或 collective。shape 标签不得压住连线或挤成小字，必要时缩放图或拆成有独立结论的一页。

## 特性图

特性图沿用模型结构图的二维表达、正交连线、英文标注、黑灰红文字和矩形状态框；是否展开模块或放大局部由内容决定。技术内容以匹配版本的 vLLM-Ascend 实际调用链为依据。仓库文档原图仍优先复用，但要与当前代码核对；HF 或论文原理图不能充当 Ascend 特性已经接入的证据。确实继承或调用上游时，继续走读对应 vLLM，不能在仓库边界截断真实路径。

- 先确定目标模型、配置、后端及特性启用条件，再将特性落到具体 Attention、MoE、缓存或调度路径上。画清原计算路径被如何切分、替换或叠加，不能只画通用特性方框。
- 首个内容页用 [模型主干与新增步骤](feature-backbone-overview.md) 定位特性：从受影响模块关联到已有计算与新增算子/collective/合并，后页再展开。新增以同一份基线和配置为参照；继承的计算不因出现在特性路径中就标为新增。
- Prefill 与 Decode 的计算、通信或状态更新不同就分开表达。实际发生的 collective 标明名称、进程组、触发位置和必要的前后 shape；AllGather、AllToAll、ReduceScatter、AllReduce 等只按代码出现，不为了凑图补入。
- 关键融合节点、通信与计算先后、必要的依赖，以及缓存/递归状态的读写交接都要保留；沿用上节的融合与 shape 核对方法。未被当前模型调用的实现、关闭的分支和 fallback 分清条件，不拼成一条虚假的全流程。
- 将节点和连线对应到源文件、符号、版本与条件，证据放底稿/备注。没有找到该特性在目标路径中的实现时明确待确认，不用 HF 小算子或其他模型的实现补成 Ascend 支持结论。
